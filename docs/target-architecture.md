# Agentized — целевая архитектура

Дата: 2026-11-10.  
Основание: [call-2026-11-10-notes.md](./call-2026-11-10-notes.md).  
Статус: согласованный черновик с принятыми решениями Максима от 2026-11-10 по границам V1. Не спецификация реализации и не утверждённый план поставки целиком; §11 фиксирует факты (принятые решения), а не открытые вопросы.

---

## 0. Факты и гипотезы

### Факты (обязательные принципы)

1. Много людей на одном проекте через своих агентов, параллельно, на пересекающихся файлах, с корректной синхронизацией.
2. Хранение всех артефактов проекта, полная историчность.
3. Скиллы и тулы для ведения проекта и синхронизации — из коробки.
4. UX: подключил репозиторий к контексту агентского проекта → система начинает работать и меняет поведение агента.
5. Когнитивный долг закрывается человекочитаемыми артефактами с полной историей плюс процессом обмена знаниями (релизы, изменения архитектуры и т.п.) в понятной форме.
6. Организационная простота: структура проекта максимально удобна для навигации самих агентов.

### Факты (аудитория)

- Продукт только для тех, кто работает преимущественно через агентов.
- Пользователи: разработчики любого стека через агентов; inner source; тестировщики (ручные, часто сам разработчик); менеджеры (PM / project manager / team lead) — бэклог, цели, приоритеты.

### Факты (референсы, проверено 2026-11-10)

**Первичный референс — Orbit Tasks** (`mpodreshetnikov/orbit-tasks`): берём **механизм**, не содержимое Orbit.

- Markdown-реестр задач в git; `INDEX.md` — генерируемая доска; lifecycle `idea→…→done`.
- Claim публикуется до правок кода; Progress и Decision Log — append-only.
- Контент задач — мелкими коммитами на `main`; правила/skills — через PR.
- Skills: `task-registry`, `task-status-sync`, `steward`; валидатор + pre-push; merge-driver для доски; ID вида `T-YYMMDD-xxx` против коллизий параллельных веток.
- Установка линкует реестр в checkout Orbit; skills под Claude Code / `.agents`.
- **Не закрывает:** UX «подключил любой репозиторий»; синхронизацию пересекающегося кода (только claim задачи на доске); multi-harness connect out of the box.

**ProjectStore** (upstream `SmartAndPoint/ProjectStore`): берём **полезные куски**, не копируем продукт.

- Git-markdown память проекта; агент предлагает артефакт, человек подтверждает; `doctor` / `reconcile`; изоляция параллельных сессий (session pointers, предупреждения).
- Upstream на `v0.30.16` (2026-11-10). Harnesses: `claude-code` и `codex`; Cursor harness в upstream отсутствует.
- Форк `mpodreshetnikov/ProjectStore` для агента ранее давал API 404 — актуальность форка как отдельного SoT не подтверждена; ориентир — полезные идеи из ProjectStore (и upstream при необходимости), не обязательная зависимость от форка.
- **Не закрывает:** параллельную работу по коду; UX «подключил — работает». Видение Agentized ≠ копия ProjectStore.

### Факты (принятые решения V1, 2026-11-10)

Сводка; развёрнуто в §11:

1. Project Context поддерживает **оба** размещения: каталог внутри code-репо **и** отдельный git-репозиторий.
2. Eng-репозиторий уже есть: https://github.com/mpodreshetnikov/agentized — первая версия живёт там.
3. Path leases в v1 только **предупреждают**, не блокируют запись.
4. В v1 — human confirmation при создании задачи (как в Orbit Tasks).
5. Digests регулярные, включая ежедневные; два типа — для разработки и для менеджмента.
6. Первичный референс — Orbit Tasks (механизм); из ProjectStore — полезные куски.
7. В v1 сразу три harness: Cursor, Claude Code, Codex.
8. В v1 — и один code-репо, и несколько репо в одном контексте.
9. Project Context — отдельная сущность, не Cursor Project Agent Store (Agent Store = файлы Cursor Project, не git).
10. Skills: harness plugin/package ставит **закреплённую копию** skills в проект (простая установка + версия в git и на review).

## 1. Суть предложения

Agentized — слой координации агентной команды поверх git:

- один **проектный контекст** (реестр артефактов + skills/tools + правила поведения);
- один или несколько **code-репозиториев**, подключаемых к этому контексту;
- агент после connect обязан: читать доску/навигацию, claimить работу (задачу и затронутые пути), писать историю, публиковать человекочитаемые итоги.

Механизм берём из Orbit Tasks. Полезные куски (подтверждение артефактов, doctor/reconcile, изоляция сессий) — из ProjectStore. Добавляем то, чего нет у обоих: **file/path sync для overlapping code** и **connect UX** сразу для Cursor, Claude Code и Codex.

## 2. Слои и компоненты

```
┌─────────────────────────────────────────────────────────┐
│  Harness (v1: Cursor · Claude Code · Codex)             │
│  skills · rules · hooks · status                        │
├─────────────────────────────────────────────────────────┤
│  Agentized runtime (из коробки)                         │
│  connect · claim · sync · validate · digest             │
├─────────────────────────────────────────────────────────┤
│  Project Context (git, markdown; in-repo и/или отдельный│
│  git-репо)                                              │
│  registry · decisions · digests · nav index             │
├─────────────────────────────────────────────────────────┤
│  Code workspaces (1..N git repos в одном контексте)     │
│  ветки · PR · path-leases (warn) · обычный code review  │
└─────────────────────────────────────────────────────────┘
```

| Компонент | Назначение |
|---|---|
| **Project Context** | Git-источник истины по работе команды: задачи, решения, дайджесты, навигация. Размещение: каталог в code-репо **или** отдельный git-репо (оба режима поддерживаются). Отдельная сущность от Cursor Project Agent Store. |
| **Registry** | Единица работы + доска + claim задачи. |
| **Path Lease Board** | Публичные аренды путей/файлов до правок кода; в v1 — предупреждение при пересечении, без блокировки записи. |
| **Runtime / Tools** | CLI/скрипты: connect, new/claim, index, check, lease, sync-status, digest. |
| **Skills** | Поведение агента: registry, sync, steward, cognitive-digest, navigate. Поставка: plugin/package → pinned copy в проект. |
| **Harness adapter** | v1: Cursor, Claude Code, Codex — правила/skills попадают в сессию при connect. |
| **Code workspaces** | Обычные репозитории продукта (один или несколько на контекст); Agentized их не подменяет. |

**Не входит в Agentized:** рантайм продукта пользователя, CI продукта (кроме опциональных проверок реестра), копирование содержимого Orbit/ProjectStore.

## 3. Как агент подключается к проекту

Целевой UX (принцип 4):

1. Есть Agentized Project Context (каталог внутри code-репо **или** отдельный git-репозиторий контекста; см. §11.1).
2. Человек/агент выполняет **connect** code-репо → Project Context.
3. Connect устанавливает:
   - связь workspace ↔ project id;
   - skills/rules Agentized в harness (Cursor / Claude Code / Codex) через plugin/package с pinned copy skills в проекте;
   - локальные hooks/validator (по возможности);
   - указатель «текущий проект» для агента.
4. С этого момента поведение агента меняется **без отдельного «не забудь про процесс»**: перед кодом — поиск/claim; во время — Progress/leases (с предупреждениями); после — sync + human digest по правилам регулярности.

**Канал доставки skills (решение 2026-11-10):** harness plugin/package, который устанавливает закреплённую копию skills в проект — простая установка, версия видна в git и на review.

## 4. Дизайн реестра

### 4.1. Что храним

В Project Context (структура **[H]**, оптимизирована под агентную навигацию — принцип 6):

```
project/
  NAV.md                 # входная карта для агента (1 экран)
  tasks/
    INDEX.md             # генерируемая доска
    T-….md               # единицы работы
    decisions/           # ADR / решения в силе
    goals/               # цели и приоритеты (для менеджеров)
  leases/
    INDEX.md             # кто держит какие пути (генерируемо)
  digests/
    development/         # регулярные дайджесты для разработки
    management/          # регулярные дайджесты для менеджмента
    releases/            # человекочитаемые релизы
    architecture/        # изменения архитектуры
  skills/                # pinned copy, поставленная plugin/package
```

Файлы задач не перемещаются при смене статуса (как в Orbit Tasks): статус в front matter.

### 4.2. Единица работы

Берём из Orbit Tasks:

- lifecycle: `idea → open → in-progress → blocked → done | dropped`;
- claim / `in-progress` **до** правок кода;
- Progress и Decision Log — **append-only**;
- ID без коллизий параллельных веток (`T-YYMMDD-xxx` или эквивалент);
- мелкие коммиты статуса на основную ветку реестра; правила — через PR;
- генерируемая доска + merge-driver / regenerate;
- **human confirmation при создании задачи** (как в Orbit Tasks) — решение V1.

Не копируем: Orbit-specific env checks, private-registry+gitignore-in-public-Orbit, содержимое задач/целей Orbit.

### 4.3. Артефакты сверх задач

Из ProjectStore-идеи, упрощённо:

- решения (ADR) с статусом и supersede;
- human-confirm на создание задачи в v1; для «тяжёлых» артефактов (ADR, digest, goals) — **[H]** confirm по аналогии с ProjectStore; рутинные Progress-апдейты — без лишнего gate;
- doctor/reconcile для согласованности индексов и ссылок.

## 5. Sync: параллельная работа и overlapping files

Два уровня синхронизации.

### 5.1. Уровень задач (факт-механизм из Orbit Tasks)

- Доска + claim задачи публикуются так, чтобы другой агент увидел занятость до старта кода.
- Append-only логи снижают merge-конфликты в теле задачи.
- Контент реестра стремится быстро попадать на общую ветку.

Этого **недостаточно** для принципа 1 (пересекающиеся файлы кода).

### 5.2. Уровень путей кода — Path Leases

Перед правкой кода агент:

1. Имеет claimed task.
2. Публикует **lease** на пути (файлы/директории) с task id, owner, expiry/heartbeat.
3. Runtime показывает конфликты: пересечение с чужим активным lease.
4. Политика v1 (**решение**): **warn-only** — агент **может** писать в те же пути; изменения должны сливаться, но агент **обязан знать** о пересечении.
5. По завершении / при sync lease снимается; код идёт обычным git (ветка/PR).

Git остаётся источником истины по содержимому. Leases — координация намерений и осведомлённости, не второй VCS и не жёсткий lock.

| Решение | Принятый вариант V1 | Альтернатива (не V1) | Почему так |
|---|---|---|---|
| Координация overlapping files | Path leases в Project Context | Только git worktrees + rebase, без leases | Без leases агенты узнают о пересечении слишком поздно |
| | | CRDT / realtime co-edit | Слишком тяжело для v0; не нужно «оптимизировать агентов» |
| Где жить leases | Markdown в том же Project Context | Отдельный realtime-сервис | Сервис ломает «всё в git / историчность» и усложняет offline |
| Конфликт | **Warn-only** (продолжить с осведомлённостью) | Fail closed (не писать) | Легитимная параллельная запись в одни пути; merge обязателен, блок мешает |

### 5.3. Несколько людей / несколько агентов

- Owner задачи — человек (ответственный), не «личность агента» (как в Orbit Tasks).
- Параллельные сессии одного человека: session isolation по идее ProjectStore (не затирать чужой контекст).
- Параллельные люди: видны через registry + leases (warn) + digests.

## 6. UX: connect → агент меняет поведение

Минимальный контракт connect:

1. **Обнаружение:** в workspace есть маркер Agentized project (файл связи / конфиг).
2. **Инъекция поведения:** skills/rules требуют registry+lease workflow (через pinned copy от plugin/package).
3. **Навигационный якорь:** агент начинает с `NAV.md` → `tasks/INDEX.md` → поиск по теме.
4. **Проверка:** `doctor`/`check` говорит, связан ли репо и свежи ли индексы.
5. **Статус в сессии [H]:** «проект X · задача Y · leases N» — чтобы человек видел, что connect сработал.

Connect не «ставит ещё один плагин ради плагина». Connect = проектный режим работы агента.

| Решение | Принятый вариант V1 | Примечание |
|---|---|---|
| Где живёт Project Context | **Оба режима:** каталог в code-репо **и** отдельный git-репо контекста | В Orbit разделение только из‑за public product / private tasks; Agentized обязан поддерживать оба |
| Harnesses V1 | **Cursor + Claude Code + Codex** сразу | Не «Cursor-only until proven» |
| Code workspaces на контекст | **1 и N** репо | Оба сценария в V1 |
| Изменение поведения | Skills + rules (pinned copy) + checklists | Жёсткие editor hooks, блокирующие write — не опора V1 |
| Agent Store vs Context | Project Context ≠ Cursor Project Agent Store | Agent Store = файлы Cursor Project, не git |

## 7. Историчность, когнитивный долг, навигация агентов

### 7.1. Историчность артефактов (принцип 2)

- Всё значимое — файлы в git.
- Не удалять задачи: `dropped`/`done` остаются.
- Decision Log / Progress — append-only; исправление = новая запись.
- ADR supersede, не rewrite истории «почему так было».

### 7.2. Когнитивный долг (принцип 5)

Два обязательных канала:

1. **Сырые артефакты** — человекочитаемый markdown (задачи, ADR, leases index).
2. **Knowledge-sharing digests** — отдельные короткие документы для людей:
   - **регулярные** (включая **ежедневные**);
   - **два типа:** для разработки и для менеджмента;
   - плюс при необходимости: релиз / поставка; изменение архитектуры; «что изменилось за период».

**Правило V1 (решение):** digests — регулярный процесс (в т.ч. daily), двух типов (development / management), а не только ad-hoc на `done`. **[H]** Дополнительный триггер «feature-sized done / значимый merge → digest или явная отметка „не нужен“» остаётся допустимым усилением поверх регулярности.

Это не замена code review и не стенограмма чата.

### 7.3. Простота навигации для агентов (принцип 6)

Жёсткие правила структуры:

- Один вход: `NAV.md` (что это за проект, где доска, где решения, где digests, как claim/lease).
- Одна доска задач, один lease index.
- Стабильные пути; без «картотек ради картотек».
- Имена и id машинно-стабильны; grep/search по id/пути/тегу достаточны для v0 (без векторного memory как SoT).
- Сгенерированные индексы можно пересобрать; источник — файлы единиц работы.

| Решение | Простой вариант | Альтернатива | Главное возражение |
|---|---|---|---|
| SoT знаний | Git markdown | Векторная memory агента | Memory не даёт общей командной историчности |
| Digests | Регулярные (в т.ч. daily) в `digests/` двух типов | Только Progress в задачах | Progress не собирает командный контекст для dev и management |
| Навигация | `NAV.md` + INDEX | Свободная wiki без входа | Агенты теряются; нарушает принцип 6 |

## 8. Что берём из референсов, что меняем

### Из Orbit Tasks — берём

- Markdown registry в git; claim до кода; append-only Progress/Decision Log.
- Генерация доски; validator; id allocator; sync статуса на общую ветку.
- Skills как носитель процесса; steward-подобное завершение сессии.
- Разделение: контент работы быстро на main; правила — через review.
- Human confirmation при создании задачи.

### Из Orbit Tasks — не берём / меняем

| Не берём / меняем | Почему |
|---|---|
| Привязка к Orbit + gitignore-в-публичном-репо | Agentized — connect любого code-репо; Context может жить in-repo или отдельно |
| Только Claude Code / `.agents` | V1: Cursor + Claude Code + Codex |
| Только task claim | Не закрывает overlapping files (нужны leases + warn) |
| Содержимое задач/целей Orbit | Берём механизм, не продукт Orbit |

### Из ProjectStore — берём

- Артефакт предлагает агент, человек подтверждает (для решений/digests; для задач — confirm как в Orbit).
- `doctor` / `reconcile` для целостности.
- Изоляция параллельных сессий / предупреждение о соседях.
- Ориентация агента от записи проекта, не от «памяти модели».
- Идея plugin/package-поставки (адаптируем под pinned copy skills в проекте).

### Из ProjectStore — не берём / меняем

| Не берём / меняем | Почему |
|---|---|
| Копия vault/epic/story модели как продукт | Нужен свой вижен Agentized |
| Ожидание Claude/Codex harness как единственного ядра | V1 сразу три harness, включая Cursor |
| Тяжёлый multi-agent critic/planner loop как обязательный v0 | Сначала connect + sync + digests |
| Memory/plugin-упаковка 1:1 без pinned copy в git | Нужны версия в git и review установленной копии skills |

## 9. Шаги к первой проверяемой версии

Проверяемая версия = команда из ≥2 людей (или 2 агентных сессий) на одном Project Context и одном или нескольких code-репо демонстрирует сценарий ниже. **Без production-кода продукта пользователей.** Первая версия живёт в eng-репозитории https://github.com/mpodreshetnikov/agentized (не docs-only в Agent Store).

1. **Зафиксировать принципы, этот черновик и принятые решения §11** (сейчас; канон в `agentized` + sync в Agent Store).
2. **Схематический skeleton Project Context** в репозитории Agentized: `NAV.md`, `tasks/`, `leases/`, `digests/{development,management}/` — без копирования Orbit content; поддержать оба размещения Context (in-repo / отдельный git).
3. **Описать connect-контракт** для Cursor, Claude Code и Codex: какие файлы появляются в workspace и какое поведение обязано включиться; plugin/package → pinned skills.
4. **Сценарий верификации V1:**
   - A connect → видит NAV/INDEX;
   - A создаёт task с human confirmation + claim + lease path;
   - B connect → видит claim/lease и получает **warn** при пересечении write-paths (запись не блокируется; merge ожидается);
   - A пишет Progress + закрывает lease + участвует в регулярном digest (dev и/или management);
   - B продолжает с актуальным контекстом;
   - опционально: второй code-репо в том же контексте.
5. **Минимальные skills (спеки → pinned copy в проекте):** registry, lease-sync, digest, navigate — для трёх harness.
6. **Runtime / docs в `mpodreshetnikov/agentized`** — не ждать отдельного «docs-only» этапа в Agent Store как SoT.
7. **Дальше по мере необходимости:** hooks harden, manager goals UI/flow, ужесточение lease-политики (если warn-only окажется недостаточным).

Критерий успеха V1: принципы 1, 3, 4, 5, 6 наблюдаемы на сценарии; принцип 2 — артефакты и история в git.

## 10. Существенные решения (опции → статус)

Для каждого: принятый вариант V1 (где есть решение) или оставшаяся опция.

1. **Где Project Context** — **решено:** оба режима (каталог в code-репо **и** отдельный git-репозиторий). В Orbit split только из‑за public/private.
2. **Где path leases** — markdown в контексте (простой вариант; альтернатива realtime-сервис отвергнута для V1 по прежним возражениям).
3. **Политика overlapping write** — **решено:** warn-only; агент осведомлён, запись не блокируется, изменения сливаются.
4. **Подтверждение человеком** — **решено для задач:** confirm при создании задачи (как Orbit Tasks). Для ADR/digest/goals — **[H]** confirm; не для каждого Progress.
5. **Harnesses V1** — **решено:** Cursor + Claude Code + Codex сразу.
6. **Форма V1** — **решено:** eng-репозиторий https://github.com/mpodreshetnikov/agentized уже есть; первая версия там, не docs-only в Agent Store.
7. **Связь с Orbit Tasks** — **решено по смыслу:** адаптировать механизм, жить отдельно от Orbit; не эволюционировать orbit-tasks в Agentized.
8. **Multi-repo** — **решено:** в V1 и один code-репо, и несколько в одном контексте.
9. **Agent Store** — **решено:** Project Context — отдельная сущность; Agent Store = файлы Cursor Project, не git.
10. **Поставка skills** — **решено:** harness plugin/package ставит pinned copy skills в проект.

## 11. Принятые решения V1 (2026-11-10)

Это **факты** (ответы Максима), не гипотезы и не открытые вопросы. Смысл зафиксирован без искажения.

1. **Размещение Project Context.** Поддерживать **оба** варианта: каталог внутри code-репозитория **и** отдельный git-репозиторий. В Orbit они разделены только потому, что продукт публичный, а задачи приватные.
2. **Где живёт первая версия.** Eng-репозиторий уже существует: https://github.com/mpodreshetnikov/agentized. Первая версия — там, а не docs-only в Agent Store.
3. **Path leases.** В v1 leases только **предупреждают**, не блокируют запись: агент может легитимно писать в те же пути; изменения должны мержиться, но агент должен быть в курсе пересечения.
4. **Human confirmation.** В v1 начинаем с подтверждения человеком при **создании задачи**, как в Orbit Tasks.
5. **Digests.** Регулярные, включая ежедневные; **два типа** — для разработки и для менеджмента.
6. **Референсы.** Первичный — Orbit Tasks (**механизм**, не содержимое Orbit). Из ProjectStore — полезные куски.
7. **Harnesses.** В v1 сразу три: Cursor, Claude Code и Codex.
8. **Число code-репо.** В v1 поддерживать и один code-репо, и несколько репозиториев в одном контексте.
9. **Project Context vs Agent Store.** Project Context — **отдельная сущность**, не привязанная к Cursor Project Agent Store. Agent Store = файлы Cursor Project, не git.
10. **Поставка skills.** Harness plugin/package, который устанавливает **закреплённую копию** skills в проект (простая установка + версия в git и на review). Согласовано Максимом 2026-11-10.

Остаточные заметки (не решения V1): доступность/актуальность форка `mpodreshetnikov/ProjectStore` (ранее API 404) не блокирует ориентацию на полезные идеи ProjectStore; бренд/имена пакетов сверх модели «plugin → pinned copy» — **[H]** при реализации.
